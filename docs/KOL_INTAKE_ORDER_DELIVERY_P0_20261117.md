# KÖL — единый процесс заявка → подтверждённый заказ → доставка

**Ветка:** `feat/kol-intake-order-link-20261117`, Draft PR #166.
**База:** утверждённый релиз #163 `7b8362f7b7caf460c0c02aa647746784fd2640f0`.
**Граница:** только тестовая Supabase/PostgreSQL. Миграции 028–032 имеют суффикс `DRAFT_NOT_APPLIED` и **не применялись к production**.

## Существующий безопасный MVP

Публичный `/checkout` записывает заявку `support_tickets`, **не** заказ и **не** оплату. Полный cart/price/address не доверяется браузеру. Служба поддержки отвечает в своей очереди. Реальные заказы до этого создавались только клиентским RPC `create_order_atomic` для самовывоза.

## Новые операции (Draft)

**028 — безопасная связь существующего заказа самовывоза с заявкой.** Проверяет клиента, состав товаров и количество, ключ `intake-<ticket UUID>`, оператора и права; фиксирует один `related_order_id`, аудит, повторы и конфликты.

**029 — подтверждение анонимной заявки клиентом.** Клиент входит через реальный Supabase Auth с **подтверждённым email** и вводит UUID исходной заявки. PostgreSQL сверяет email из заявки, `auth.users.email_confirmed_at`, активную роль `client`; телефон **не считается доказательством личности**. Отдельный RPC и форма на `/client/support`. Без email / email неподтверждён / чужая заявка → отказ.

**030 — тариф доставки KGS.** Частная таблица `private.kol_delivery_tariffs` содержит только утверждённые активным администратором тарифы партнёр × зона. Никакой ставки по умолчанию. Оператор запрашивает через RPC стоимость только для существующей заявки, разрешённой зоны и конкретного утверждённого партнёра. Адрес требует ручного подтверждения. Тариф по умолчанию отсутствует — операция запрещена. В базе нет production-ставок: 180 сом используется исключительно как тестовый тариф.

**031 — общий атомарный механизм создания заказов.** Существующий клиентский путь `create_order_atomic` продолжает использовать idempotency wrapper 008a и допускает **только pickup**. Операторский и клиентский пути используют **один внутренний расчёт**: цена из каталога, блокировка товаров, списание остатков, snapshot позиций, начисление доставки, pending-платёж, `order_delivery`, `deliveries`, история и аудит. Внутренняя функция недоступна непосредственно через JWT/Data API.

**032 — операторское подтверждение.** `admin_confirm_intake_order_atomic(ticket,business,fee,confirmation_note,request_id)` доступен только `support_admin/super_admin`. Он проверяет созданную/закреплённую заявку `order_request`, роль клиента, его подтверждённый email, однородную корзину одного партнёра, обязательные условия заказа, согласованную комиссию и адрес. Тариф перечитывается с блокировкой в **той же транзакции**. Статусы, склад, сумма и доставка фиксируются атомарно. `related_order_id` сохраняет единый ключ для всех этапов. Повтор с тем же `request_id` не создаёт новую операцию; изменённый запрос отвергается. Платёж остаётся `pending`.

## Ограничения перед production

- Ни одной живой цены доставки нет: тарифы должны быть занесены и утверждены администратором на основании коммерческих правил; нельзя копировать QA-ставку.
- Автоматическая оплата, провайдеры эквайринга и зачисление денег не реализованы этим PR. **Доставка `delivered` не означает `paid`**: `payment_status` остаётся `pending`.
- Для анонимных заявок без email нельзя создавать заказ на основании одного телефона. Нужна отдельная подтверждённая личность/контакт и согласие.
- В одной заявке с несколькими партнёрами/типами товаров нет безопасного объединения в один заказ: пока отказ, а разбиение требует отдельного контракта.
- Миграции должны пройти общий CI и независимую проверку основного клиентского RPC, старых операций партнёра, склада, бронирований и RLS.
- Необходимы проверка реальной целевой Supabase, резервная копия **вне Ubuntu**, восстановление, проверка домена, откат и отдельное разрешение на production.
- Дизайн OriginalWinterStage и существующие экраны не заменять. Другие проекты, MARINA SMART, AI PROF, n8n не трогать.

**Примечание:** исходные ID не обязаны совпадать: связываем `support_tickets.id`, `orders.id`, `order_delivery.order_id`, `deliveries.order_id` через внешние ключи и аудит; никаких дубликатов по `request_id`.
