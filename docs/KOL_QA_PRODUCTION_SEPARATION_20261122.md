## Проверенная конфигурация

- Единственный доступный активный Supabase-проект КЁЛь: **`kol-travel-platform-test`** (`mphruawzozrpwcjgejhs`). Новая Production-БД КЁЛь **не обнаружена** среди подключённых проектов пользователя.
- Vercel-проект `kol-launch-staging-20260925` содержит веточный Preview текущего PR #172. Его `/api/health` показывает `environment=preview`, `dataSourceMode=supabase`, `databaseConnectivity=reachable`, `operationalReadiness=not_verified`.
- `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` назначены **одними переменными на оба target: Preview + Production**. Их необходимо разделить. **Не читать/не публиковать значения**, пока не готово целевое окружение.
- `DATA_SOURCE_MODE` и `KOL_DEMO_ACCESS` также имеют общие target Preview + Production. Кроме того, существует веточная настройка Preview для release/kol-unified-p0-20261120, которая может переопределять общую.
- `SUPABASE_SERVICE_ROLE_KEY` присутствует как отдельная Production-переменная и отдельная Preview-переменная для текущей release-ветки. Их фактическое значение по этому аудиту **не сверялось**, а имя не гарантирует принадлежности к нужной базе.
- `PRODUCTION_RUNTIME_IMPLEMENTATION_READY=false` в `src/lib/deployment-safety.ts` намеренно блокирует перевод текущего релиза в Production. **Не включать преждевременно**.
- Vercel домен `kol.on.kg` привязан к ветке `audit/kol-p0-hardening-isolated-20261119-gpt6`, а реальный DNS пока ведёт на Hoster.kg; сертификат `localhost` не годится для публичного домена.

## Строгий способ разделения

1. Сначала закрыть миграционный реестр `docs/KOL_MIGRATION_RECONCILIATION_20261122.md` и доказать clean-room replay без ручных, скрытых SQL.
2. Определить Supabase organization для Production и согласовать возможную стоимость нового проекта. До этого **не создавать** платный проект и не менять подключённую тестовую базу.
3. Создать **отдельную** Production Supabase. Не клонировать действующие QA Auth-сессии, временные логины, фиктивные платежи, тестовые тарифы или коммерческую историю; создать минимальный пустой каталог и отдельно разрешённые реальные записи.
4. Настроить отдельные ключи только в целевых target Vercel: Preview → тестовый проект, Production → Production-проект. Секретная служебная роль должна оставаться на сервере, вне `NEXT_PUBLIC_*`.
5. Проверить `KOL_DEMO_ACCESS=false`, `DATA_SOURCE_MODE=supabase`, production URL/redirect/callback, Auth/RLS/Storage и защиту платежей.
6. Провести на отдельной Production-БД post-migration READ-ONLY проверки, затем без платежей проверить с анонимного клиента `/api/health`, публичные маршруты и отсутствие данных чужой организации.
7. Получить Authorised JWT/role E2E на **отдельных** тестовых идентичностях Production, безопасно удалить QA после завершения и подтвердить baseline. Никогда не выполнять облачный QA, настроенный на `mphruawzozrpwcjgejhs`, против Production URL.
8. После подписанного акта приёмки production-runtime изменить защитную константу отдельным просматриваемым PR. Отдельно выполняется коммерческая публикация каталога, платёжная интеграция, DNS и HTTPS.

## Безопасность и откат

- Никакое отключение безопасного шлюза production, перенос домена или перепривязка глобального `NEXT_PUBLIC_SUPABASE_URL` не допустимы **до** независимой проверки ключей и новой БД.
- Сохранить отдельно работающий Preview и исходные записи TEST; тестовая Supabase служит источником только для **сверки схемы**, а не копирования коммерческих данных.
- Внешний бэкап текущей TEST и независимо восстановимая Production-схема обязательны. Хранить средства расшифровки вне сервера и GitHub-артефакта; исключить вывод паролей из логов.
- Нет фактических банковских операций и подтверждённых коммерческих дат — эти P0 нельзя обходить конфигурационным флагом.
