## 1. Подтверждение коммерческих номеров

Исходный реестр создан из облачной базы **только на чтение**:

- /home/agent/kol-ops/reports/KOL_PARTNER_CONFIRMATION_20261106_v2/rooms_partner_confirmation.csv — 34 номера, четыре реальных объекта;
- /home/agent/kol-ops/reports/KOL_PARTNER_CONFIRMATION_20261106_v2/tours_partner_confirmation.csv — только заголовки: реальных туров сейчас нет.

Все 34 номера имеют исходный статус **under_review**; у **15** из них записана неположительная цена (8 Ак-Бермет, 5 Бакыт, 2 Три Короны). Реестр v2 отмечает их **price_review_required=YES**; для таких номеров проверка подтверждения даты требует явно указанной положительной цены от партнёра. Сначала собственник/администратор должен проверить и утвердить соответствующие карточки (с применением предусмотренного ролевого workflow). Нельзя автоматически переводить их в active.

В колонке listed_price_kgs_unverified показана цена из текущей карточки **без подтверждения актуальности**. Это не подтверждённый коммерческий тариф. Для реальной продажи партнёр указывает дату (YYYY-MM-DD), реальное количество доступных номеров, при необходимости подтверждённую цену в KGS, имя подтвердившего и дату-время подтверждения с часовым поясом.

Проверка заполненной CSV выполняется:
```bash
python3 scripts/prepare-kol-partner-inventory.py --validate-rooms /home/agent/kol-ops/reports/KOL_PARTNER_CONFIRMATION_20261106_v2/rooms_partner_confirmation.csv
```
Валидация проверяет структуру, но **не удостоверяет реальность** подписи партнёра. Записи должны публиковаться только авторизованным партнёром через существующую форму /partner/availability/rooms и проверенный серверный RPC — **после** применения соответствующих миграций. Этот CSV не загружается автоматически в облачную базу.

Демонстрационный объект и тур исключены из рабочих CSV по фиксированным ID; существующие публичные списки приложения уже фильтруют эти ID. Удалять демонстрационные строки из базы сейчас не нужно.

## 2. Вынесение ключа восстановления на отдельный MacBook

На Ubuntu уже создан зашифрованный внешний архив в приватном GitHub; *ключ расшифровки в GitHub не сохраняется*. MacBook виден через Tailscale, но на момент аудита был офлайн. Поэтому **реального хранения ключа на Mac пока нет**.

В репозитории приготовлены:
- scripts/kol-emit-recovery-key-ssh.py — выдаёт ключ только внутри аутентифицированной SSH-сессии по запросу выделенного скрипта; локальный запуск отказан;
- scripts/kol-mac-recovery-keychain.swift — сохраняет секрет через macOS Security.framework в Keychain, выполняет readback, не показывает ключ;
- scripts/kol-mac-escrow-from-ubuntu.sh — одноразовый запуск на Mac: проверяет macOS, компилирует Swift во временную папку, передаёт ключ по SSH непосредственно в Keychain.

**На MacBook, после включения Tailscale и проверки SSH-доступа к Ubuntu:**
```bash
git clone --branch integration/kol-unified-20261105 https://github.com/stvelikiy-star/kol-travel-platform.git ~/kol-recovery-setup
cd ~/kol-recovery-setup
bash scripts/kol-mac-escrow-from-ubuntu.sh YOUR_UBUNTU_TAILSCALE_IP
```
Если каталог уже существует — обновить ветку обычным git pull вместо повторного git clone.

Успешное сообщение: KOL_MAC_KEYCHAIN_ESCROW_READBACK_PASS или KOL_MAC_KEYCHAIN_ESCROW_ALREADY_PRESENT_MATCHES_PASS. Если SSH-ключи или проверка доверенного host key не настроены — скрипт завершится без записи.

В Keychain секрет хранится под Service = **KOL-OFFSITE-RECOVERY-2026**, Account = **KOL_BACKUP_KEY**. Атрибут **ThisDeviceOnly** преднамеренно предотвращает несанкционированную синхронизацию; при потере и Mac, и Ubuntu потребуется ещё одна отдельная защищённая копия в менеджере паролей или аппаратном сейфе. Проверка Mac на другом устройстве и фактическое восстановление после полной потери Ubuntu пока **NOT VERIFIED**.
